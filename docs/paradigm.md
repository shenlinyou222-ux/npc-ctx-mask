# 一种多智能体交换信息的新范式：以 KV 块为媒介

## 一句话

**把"智能体之间传话"从文本层下沉到缓存块层**：所有智能体共享一份 prefill 缓存，用块级掩码控制各自能看到什么；子智能体的结论写回主序列预留的槽位，主智能体解除掩码后直接读到。

传统做法是"生成文本 → 拼进下一轮 prompt → 重新 prefill"；这里变成"写进同一个缓存 → 改一块可见性"。

## 完整中文例子（已跑通）

**共享档案（主、子都能看到）**

```
一、仓库的龙门吊在周一下午做过保养。
二、夜班值班员报告当夜没有异常。
```

**子智能体额外 prefilled 的私有记录（主智能体看不到）**

```
私有记录：阀门 DANDAN-9171的冷却液编码是KARTHA-7346。
```

主智能体在同一段位置看到的是 43 token 的中性填充。**共享档案里没有答案。**

**子智能体生成**（prefill 长度 68 token，生成从这里开始）

```
阀门 DANDAN-9171 的冷却液编码为 KARTHA-7346。
```

**主序列与槽位**

```
共享档案(25) + 中性填充(43) + [槽位 48] + 问题一 + 问题二 + 先答问题二
槽位区间 = [68, 116)，与子智能体生成起点对齐 ✔
```

**时序：先答能答的，再答要等的**

| 臂 | 先答问题二 | 再答问题一 |
|---|---|---|
| full（槽位放文本） | ✔「周一下午。」 | ✔「KARTHA-7346。」 |
| **swap（槽位换 K/V）** | ✔「周一下午」 | ✔「KARTHA-7346」 |
| **noswap（不替换）** | ✔「周一下午」 | ✘「DANDAN-9171」← 把阀门名当成了编码 |

读法：

1. **主智能体不空转**：槽位还是占位时，它先把问题二答了；
2. **之后才注入子智能体的 K/V**，并 prefill 一句「子智能体已返回，现在回答问题一」；
3. **它回头答出了问题一**，而 `noswap` 明确答错——证明答案来自私有上下文，不是共享档案。

## 三个部件

| 部件 | 作用 | 状态 |
|---|---|---|
| **共享前缀** | 一份缓存被 N 个角色/分支复用，不重复 prefill | ✅ 已验证（TTFT 0.98s → 0.06s，16×） |
| **块级掩码** | 请求级声明"哪些块我不可读"，注意力层物理剔除 | ✅ 已验证（canary 8/8 可见 / 0/8 泄漏） |
| **预留槽位 + 写回** | 主序列留一段位置，子智能体的结论写进去，再解除掩码 | ✅ 已验证（20/20 = 重 prefill 20/20，不写回 0/20） |

## 与传统多智能体的差别

| | 传统 | 本范式 |
|---|---|---|
| 交换媒介 | 文本 token | KV 块（也可是整句） |
| 交换成本 | 重新 prefill 整段上下文 | 改指针 / 换 K/V，接近零拷贝 |
| 可见性控制 | 删文本 或 提示词约束 | 引擎级掩码，模型物理读不到 |
| 缓存复用 | 每次可见集变化即失效 | 可见集变化不影响缓存命中 |
| 并发 | 串行依赖 | 共享前缀的并行分支，结束后汇总 |

## 已验证的证据

| 结论 | 数据 |
|---|---|
| 掩码是硬的，不是软的 | 可见块 8/8 读得到，被遮块 0/8；与物理删除一致 |
| 掩码不损质量 | ZZZ 60 题：全塞 57/60 = 遮蔽 57/60 |
| 掩码挡住越界 | 受限条件下泄漏 57/60 → **0/60** |
| 槽位热替换等价于重 prefill | 20/20 vs 20/20，不替换 0/20 |
| **子智能体真实生成 + 整句写回** | full 5/5、**swap 4/5**、noswap 0/5 |
| 掩码可运行时切换 | deny → open → deny 三步全对 |

## 四条硬约束（都是实测出来的）

1. **返回必须是自包含的陈述句**
   槽位里放完整句（`The valve code for X is Y.`）→ 20/20；
   只放裸答案（`Y`）→ 0/6，主智能体无法把它和问题关联起来。

2. **必须显式告知"子智能体回来了"**
   只说 `Sub-agent returned:` → 5/20；
   说清"已完成 / 结果在上面 / 现在可以用" → 20/20。
   连"内容本来就在槽位里"的上限臂也受这句影响（15/20 → 20/20）。

3. **位置必须对齐**
   子智能体写入的位置要和槽位一致，否则要重旋转（我们的数值验证未通过）。
   给请求加"起始位置"而不动块表会直接 **CUDA illegal memory access**。
   正确原语是**块表别名**（共享物理块 + 引用计数），不是位置偏移。

4. **子智能体必须带着共享前缀生成**
   在零上下文里生成的总结，K/V 表示太弱，写回去也没用。

## 现在缺的引擎能力

| 能力 | 现状 |
|---|---|
| 请求级块可见性 | ✅ 我们打了 patch |
| 运行时切换可见性 | ✅ 已有（按 mtime 重读） |
| **块表别名**（子请求写进主请求的块） | ❌ 需新增：`ref_cnt++` + 指定 block_table + 起始位置 |
| 块级 KV 注入（把已完成请求的 K/V 写进别处） | ❌ 不需要——块表别名更简单 |

## 边界：不声称的东西

- 掩码**不**提升准确率（随机干扰下无差异）；
- 掩码**不**诱导拒答（M 0/60，删文本 60/60）；
- 位置预算约 32K，且只在 1.7B 上测过；
- 多分支（>1 个槽位）、多模型都未测。

## 为什么是现在

三条曲线在收敛：

- **缓存变便宜**：DeepSeek V4.1-Flash 已做到 890 B/token（比 Qwen3-1.7B 的 112 KiB 省 129×）；
- **窗口变长**：1M 上下文；
- **块索引已是原生设计**：V4.1 的 `candidate_block_size=8`、`kv_source_layer_ids`。

窗口越长、缓存越便宜，"每次重拼上下文"的浪费占比就越高；而"块表 + 可见性"本来就是新一代引擎的形态，只差一层业务语义。

## 结论

> 多智能体之间交换的可以不是文本，而是**缓存块**；控制信息流动的可以不是提示词，而是**块级可见性**。
> 这让"分叉—并行—汇总"的代价从"重算整段上下文"降到"改一个指针"。

已实现的部分（掩码、槽位、热替换、真实子智能体）在单卡 8GB 上跑通；缺的一块（块表别名）有了明确设计，等引擎支持。
