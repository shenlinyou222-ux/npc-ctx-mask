# 多槽位：子智能体回答后回填槽位（正式版）

## 机制

```
① 子智能体 k 在自己的**私有上下文**里生成结论（正常生成，无位置技巧）
② 把结论**回填**到主序列的槽位 [P_k, P_k+L)
③ 解除该段掩码
④ 主智能体读到内容后作答
```

**关键在第 ② 步**：被遮的块原本没有内容；子智能体答完，把那段文字 prefill 回原位，块才有内容。不是"生成时就落在那个位置"。

## 结果

| NS | 都填 | 都不填（保持遮蔽） | 只填第 2 个 |
|---|---|---|---|
| 3 | **12/12** | 0/12 | 4/12 |
| 5 | **20/20** | 0/20 | 4/20 |

- **都不填 = 0**：块没内容时，模型只能瞎编（输出 `1234`）或说找不到 → 这就是"被遮住"的状态；
- **只填第 2 个 = 4/12（4/20）**：每个 trial 恰好命中 1 个，就是第 2 个；
- **都填 = 满分**。

## 一个必须配的协议句

`只填第 2 个` 时，模型会把同一个编码填给其他空位（"乱填空"）。加一句即归零：

> Answer Qk only. Then reply exactly "I don't know" for the others.

（vLLM 侧实测：污染 10 次 → 0 次，命中率不变 6/6）

## 两条走不通的路（已记录为 ERRATA）

| 做法 | 结果 | 原因 |
|---|---|---|
| 用 `position_ids` 覆盖，把生成硬放到槽位位置 | swap **0/5**（对照 full 5/5） | HF 里显式 position_ids 与 KV cache 不兼容 |
| 把子智能体前缀填充到与槽位等长再生成 | **n=0/160** | 填充放在指令前，模型跑去总结共享前缀 |

**正确的做法是"先答，再回填"**，而不是"在位置生成"。这也顺带解释了为什么返回必须是完整陈述句（裸答案 0/6，完整句 20/20）——它要作为内容被 prefill 进去。

## 真实顺序已验证（答案只对槽位之前的缓存做 prefill）

`incremental` 臂：前缀+空槽+问题**先算好存进缓存**，答案到达后**只用 [0,P) 的缓存**给答案 token 做 prefill，
把得到的 K/V 放进 [P, P+len)，后缀 K/V 不重算，之后继续 decode。

| 做法 | 命中 |
|---|---|
| `inline`（整条重算） | 6/6 |
| `incremental`（只对前缀 prefill，后缀不重算） | **6/6** |
| `empty`（不填） | 0/6 |

两种做法一致，说明此前多槽位数据（12/12、20/20）没有被"重算顺序"污染。
`empty` 臂会把实体名答对、编码编成 `12345`，说明它读到了上下文，只是槽位没内容。
