# 动机：专有知识库上的多智能体 RAG，时间花在重复 prefill 上

## 场景

- **专有知识库**：固定、有界、可预载（不是开放域检索）
- **多智能体流程**：一次提问经过 3–5 次模型调用
- 每次调用都是**长上下文 + 短输出**

## 实测成本（Qwen3-1.7B，单序列，8 GB 卡）

| 上下文 | prefill | decode |
|---|---|---|
| 2K | 0.273s（7337 tok/s） | 0.034 s/token（30 tok/s） |
| 8K | 2.006s（3988 tok/s） | 0.036 s/token（28 tok/s） |

**生成 1 个 token 的时间 ≈ prefill 55 个 token（8K 档）。**

交叉点：8K 上下文下，输出超过 **55 个 token** 时 decode 才开始主导。

## 一次提问的分解（8K 上下文，30 token 输出，4 次调用）

| 环节 | prefill | decode | 合计 |
|---|---|---|---|
| 规划 | 2.0s | 1.1s | 3.1s |
| 生成检索 query | 2.0s | 0.4s | 2.4s |
| 读文档作答 | 2.0s | 1.1s | 3.1s |
| 核验 | 2.0s | 1.1s | 3.1s |
| **合计** | **8.0s** | 3.7s | **11.7s** |

**prefill 占 68%。**

## 为什么现有缓存救不了

四个环节用的文档集不完全一样：

- 规划：只有系统提示 + 问题
- 生成 query：加检索结果
- 读文档：加更多文档
- 核验：加草稿

**每换一次文档集，前缀就变，前缀缓存的键就失效，全部重算。**

上下文缓存 API（OpenAI / Anthropic / Gemini）也一样——它们缓存的是"逐字节相同的长前缀"。

## 我们的做法

```
一次 prefill：把候选文档全部放进去，位置固定，预置为不可见
每次调用：只改掩码 —— 这次允许看哪几块
```

| 做法 | 4 次调用的 prefill |
|---|---|
| 每次重拼 | 4 × 2.0 = **8.0s** |
| 掩码切换 | 2.0 + 3 次切换（≈0）= **2.0s** |

总时延从 11.7s 降到约 5.7s。

## 成立条件（缺一不可）

| 条件 | 说明 |
|---|---|
| 知识库固定且有界 | 预载一次，长期复用 |
| 文档能装进窗口 | 2K–16K 可行；更大需分片 |
| 各环节只是**可见子集不同** | 这正是掩码能表达的差异 |
| 输出较短 | 长文生成时 decode 主导，prefill 优化占比下降 |

## 明确不适用

- 开放域检索（每次检索结果不同、语料装不下）
- 单次调用、无分支的场景（前缀缓存本来就够）
- 需要超长输出的环节（写报告、生成代码）

## 一句话

> 多智能体 RAG 的瓶颈不是生成，是**每次调用都重读一遍几乎相同的上下文**。
> 而这批上下文大部分是同一批文档，只是可见范围不同。
