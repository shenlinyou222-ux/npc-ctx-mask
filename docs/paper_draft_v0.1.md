# 世界观 RAG 的上下文掩码：用请求级 KV 块屏蔽实现角色信息边界

> 草稿 v0.1 · 2026-10-27 · 模型 Qwen3-1.7B + vLLM 0.30（`FLEX_ATTENTION`），RTX 5060 8GB
> 所有数字均来自本仓库实测，实验清单见附录 A。未验证的结论在正文中显式标注。

---

## 摘要

角色扮演与世界观问答系统要求 NPC **只知道他这个角色该知道的事**：不知道未来剧情、不知道别的地区、不知道别的角色的秘密。现有做法要么把不该看的文本删掉（每次可见集变化都要重建上下文），要么靠提示词约束（模型可以被诱导绕过）。

我们提出**请求级 KV 块屏蔽**：世界观语料只 prefill 一次，每个请求携带一个"可见性标签"，引擎在注意力层把不该看的块从 KV 索引中剔除。实验表明：

- **屏蔽是精确的**：同一上下文内，可见块的 canary 8/8 读得到，被屏蔽块的 canary 0/8 读不到，与物理删除行为一致；
- **质量无损**：可见内容相同时，屏蔽 24%–97% 的块，准确率与不屏蔽、与文本删除三者一致；
- **速度提升 16×**：token 序列不变 → 前缀缓存命中，TTFT 0.98s → 0.06s；
- **位置有独立预算**：距离超过约 32K（本模型）后检索精度衰减，80K 掉到 50%，160K 失效；位置压缩可把 160K 间隙压回 40K 有效距离并完全恢复。

我们另外给出一个可复用的**位置预算标定流程**（不占显存、约 1 分钟）与一套工程规则，并发布一个版本可见性数据集（绝区零 2.0–3.2）作为案例。

**定位**：这不是"又一个 RAG 技巧"，而是把**上下文管理从 agent 侧移到引擎侧**——agent 只声明身份与进度，引擎按块标签决定可见集并管理缓存生命周期。缓存越便宜（量化 / offload / 层级共享），这个迁移的收益越大。本文同时公开引擎 patch、全部实验脚本、原始结果与踩坑记录。

## 1. 引言

### 1.1 场景

一个世界观 RAG 系统通常包含：

- 一份**世界资料**（地点、阵营、角色、事件、术语），规模从几万到几十万 token；
- **多个角色**（NPC），每个角色的知识边界不同：三月七不知道匹诺康尼的真相，贝洛伯格的居民不知道仙舟的事；
- **时间/剧情进度**：同一个角色在 1.0 和 3.0 知道的东西不同。

系统需要在一份共享语料上，为每个"角色 × 剧情进度"组合提供不同的可见集合。

### 1.2 现有做法及其代价

| 做法 | 问题 |
|---|---|
| **文本删除**：每次只拼可见文档 | 可见集一变，token 序列就变 → 前缀缓存全部失效，每次都要重 prefill |
| **提示词约束**："不要提及 X" | 软约束，可被诱导；且模型知道内容，只是被要求不说，泄漏风险始终存在 |
| **每角色一份缓存** | 磁盘/显存线性膨胀；场景数 × 角色数不可控 |

### 1.3 我们的做法

**只 prefill 一次，用请求级标签在注意力层控制"谁能被读到"。**

关键点：屏蔽不改变 token 序列，因此前缀缓存完全复用；同时屏蔽发生在注意力之前，模型**物理上读不到**被屏蔽内容，而不是"被告知不要提"。

### 1.4 工程定位：把上下文管理从 agent 侧移到引擎侧

传统 RAG 里，**上下文管理是 agent 的活**：每次请求自己决定"这次要拼哪些文档"，然后整段重新 prefill。这个模式下：

- 可见集一变，prompt 就变，前缀缓存全部失效；
- 同一份语料被 N 个角色重复 prefill N 次；
- agent 只能通过"删文本"来控制可见性，控制粒度就是文档，做不到"同一份缓存、不同视角"。

我们的做法把这个职责**下推到引擎**：

```
agent 侧：  "我是三月七，进度 2.4"        （声明意图，不需要拼上下文）
引擎侧：    块存储 + 块标签 + 每请求可见集合 + 缓存生命周期
```

这给引擎提了五个新要求：

| # | 引擎能力 | 现在有没有 | 说明 |
|---|---|---|---|
| 1 | **块级可见性声明**（请求级黑名单） | 我们打了 patch 实现 | 改动量很小：块表 + 索引剔除 |
| 2 | **块元数据**（场景/租户/版本/原始位置） | 需要新增 | 标签体系的载体 |
| 3 | **按标签管理缓存**（淘汰/offload/恢复） | 没有 | 现在只有 LRU，不认标签 |
| 4 | **位置记账**（块保留原位置，压缩策略可配置） | 没有 | 决定"位置预算"能否被引擎自动管理 |
| 5 | **可观测性**（本次读了哪些块、泄漏审计） | 没有 | 合规场景必需 |

**为什么现在做这件事**：过去缓存贵，大家默认"少放一点、每次重拼"；而 KV 缓存的成本正在快速下降——

- KV 量化（fp8 等）：容量 ×2；
- CPU/NVMe offload：容量 ×10（我们实测 `--kv-offloading-size 12` 可跑）；
- 层级/共享缓存（多请求共享前缀、按层缓存）：同一份语料的摊销成本继续下降。

缓存越便宜，"可见集变化导致重 prefill"的代价就越不可接受——因为**浪费的不是显存，是已经算好的算力**。反过来，当缓存不再是瓶颈，把控制面放到引擎侧（块标签 + 每请求可见集）就成了自然选择。

本机实测的容量基线（单卡 8GB，Qwen3-1.7B，约 112 KiB/token）：

| 配置 | KV 容量 | 相当于 |
|---|---|---|
| bf16，GPU | 27,136 token | 1.66 × 16K 并发 |
| + CPU offload 12 GiB | 约 10 万 token | 约 6 × 16K |
| + fp8（当前后端不支持） | ×2 | — |

也就是说，**同一个 1.7B 模型，换缓存架构后能装的内容差一个数量级**——而掩码机制本身不需要改，它只依赖"块有标签、请求能声明可见集"。

这也是我们说"有上升空间"的具体含义：**位置预算（约 32K）和缓存容量都会随着模型与缓存架构改善而变大，而掩码带来的收益（缓存命中 + 安全边界）是跟着放大的**。

## 2. 方法

### 2.1 块粒度与对齐

引擎的 KV cache 以 16 token 为块（FlexAttention 硬性要求）。要让"文档"与"块"一一对应，需要把每篇文档补齐到块边界：

```
块起点 a = ceil(当前 token 数 / 16)
追加「文档正文 + 换行」
补零宽字符 \u200c 到 16 的整数倍
块终点 b = 当前 token 数 / 16
```

零宽字符在 Qwen 分词器里严格 1 字符 = 1 token，不改变语义（已验证）。这样每篇文档恰好占整数个块，相邻文档不共享块。

### 2.2 请求级可见性

请求携带 `request_id = "scope=<标签>|<任意后缀>"`，引擎按标签查一张 `{标签: [[块起, 块止), ...]}` 的**黑名单**：

- 列出的块从该请求的 KV 索引中剔除；
- 未列出的块（包括新生成的 token）正常可见；
- 同一批里不同请求可以带不同标签，互不影响。

我们早期用过白名单（只列可见块），结果模型自己生成的块也被屏蔽，输出退化。**必须用黑名单语义。**

### 2.3 场景切分与 prefill 分割

世界观语料按"场景"分组（同一地点、同一剧情段的所有条目），每个场景对应一段连续块。可见集合 = 若干场景的并集。

系统启动时：

1. 把全部场景拼成一条长序列，prefill 一次，缓存落地；
2. 为每个"角色 × 进度"生成一个标签，记录它**不可见**的场景块区间；
3. 服务时按标签屏蔽。

这样 N 个角色共享一份缓存，代价只有每请求一个块列表。

### 2.4 缓存开销实测

所有数字来自本机（RTX 5060 8GB）真实启动日志，不是估算。

**Qwen3-1.7B**（`num_hidden_layers=28`，`num_key_value_heads=8`，`head_dim=128`，bf16）：

```
每 token KV = 2（K,V）× 28 层 × 8 头 × 128 维 × 2 B = 114,688 B = 112 KiB
```

| 实测项 | 数值 | 与公式核对 |
|---|---|---|
| `Available KV cache memory` | 2.44 GiB | — |
| `GPU KV cache size`（8K 配置） | 22,864 token | 22,864 × 112 KiB = **2.442 GiB** ✔ |
| `GPU KV cache size`（16K 配置） | 27,136 token | 27,136 × 112 KiB = **2.899 GiB** ✔ |
| 单个 16K 请求实际占用 | 1.75 GiB | 16,384 × 112 KiB ✔ |
| 权重 + 非 torch | 3.36 GiB | vLLM 日志 |
| 8K 服务常驻显存 | 7,441 MiB / 8,151 MiB | 几乎占满 |

**跨模型对比（每 token KV 成本，bf16）**：

| 模型 | 架构 | 每 token KV | 2.9 GiB 池可装 |
|---|---|---|---|
| **Qwen3-1.7B**（本实验） | GQA，28 层 × 8 头 × 128 | **112 KiB** | 27K token |
| DeepSeek-V3 级（参考） | MLA，61 层 × (512+64) | **≈ 69 KiB** | 44K token |
| DeepSeek-V4.1-Flash | **待填** | — | — |

> 更新：V4.1 的数字已从官方模型卡查到，见下表。

**跨代对比（全部来自各自官方 config / model card）**：

| 模型 | 每 token KV | 相对本实验模型 | 2.9 GiB 池可装 |
|---|---|---|---|
| **Qwen3-1.7B**（本实验，GQA 28×8×128，bf16） | **114,688 B（112 KiB）** | 1× | 27K token |
| DeepSeek-V3.2（MLA 61×(512+64)，bf16） | 70,272 B（68.6 KiB） | 0.61× | 44K token |
| DeepSeek-V4-Flash（按 README：890×4） | ≈ 3,560 B（3.5 KiB） | 0.031× | ≈ 870K token |
| **DeepSeek-V4.1-Flash**（FP4 主 KV + CSA2 层间共享 + CED） | **890 B** | **0.0078×（129× 更省）** | ≈ 3.5M token |

来源：`deepseek-ai/DeepSeek-V4.1-Flash` 的 `config.json`（40 层、64 头、`num_key_value_heads=1`、`head_dim=512`、`qk_rope_head_dim=64`、`max_position_embeddings=1048576`、`rope_scaling=yarn factor 16`）与 README 原文：

> "Combined with FP4 main KV caching (E2M1 format, one E4M3 scale per 16 channels), these designs reduce the global KV cache footprint to **890 bytes per token** — roughly 1/4 of DeepSeek-V4-Flash."

**这张表最重要的结论**：一个 **1.7B** 小模型的 KV 开销（112 KiB/token），比 **671B 的 DeepSeek-V3.2**（68.6 KiB/token）还高 1.6 倍，比 **V4.1-Flash**（890 B/token）高 **129 倍**。

原因是架构选择，不是模型大小：

| 手段 | 省多少 |
|---|---|
| GQA → MLA（压缩成 576 维 latent） | 1.6× |
| + 跨层共享（CSA2：Full / Reindex / Reuse 三种层模式） | 进一步数倍 |
| + FP4 主 KV（E2M1，每 16 通道一个 E4M3 scale） | 4× |
| + CED（解码器全局 KV 由编码器末层投影，不再逐层派生） | 显著 |

**对本文的直接意义**：V4.1-Flash 的 1M 上下文和 890 B/token，正是"缓存变便宜 + 窗口变长"的实证。在 2.9 GiB 的 KV 预算下：

- Qwen3-1.7B 只能装 **2.7 万** token；
- V4.1-Flash 能装 **350 万** token。

**而我们的掩码机制一行都不用改**——它只依赖"块有标签、请求能声明可见集"。更重要的是，V4.1 的 CSA2 本身就是**块粒度**的（`candidate_block_size=8`、`index_topk=512`、`candidate_topk_blocks=2048`），说明"引擎持有块表并按规则选择"已经是新一代架构的默认形态，而不是我们额外的需求。

## 3. 实验

### 3.1 屏蔽是否精确（canary）

构造：同一上下文里放两个唯一编号，一个在可见块，一个在被屏蔽块，分别提问。

| 条件 | 读到被屏蔽编号 | 读到可见编号 |
|---|---|---|
| 不屏蔽 | **8/8** | 8/8 |
| **块屏蔽** | **0/8** | **8/8** |
| 物理删除 | 0/8 | 8/8 |

**屏蔽与删除在行为上完全一致，且正对照证明模型不是"一律拒答"。**

### 3.2 质量是否受损

三份语料、三种遮蔽比例：

| 语料 | 遮蔽比例 | 全塞 | 块屏蔽 | 文本删除 |
|---|---|---|---|---|
| Baroque（真实 wiki，2.9K token） | 51% | 10/10 | 9/10 | 10/10 |
| HotpotQA（噪声对照，7.5K） | 97% | 22/24 | 22/24 | — |
| 绝区零（版本可见性，60 题） | 24% | 58/60 | 58/60 | 58/60 |

**在 24%–97% 的遮蔽比例下都没有观察到质量代价。**

早期曾观察到"屏蔽后准确率下降"，后来定位为两个实现/度量问题：判分过严（答案少了括号里的英制单位被判错）与 `max_tokens` 截断。修正后差异消失。

### 3.3 速度

| 条件 | TTFT 中位 | 说明 |
|---|---|---|
| 全塞（首次 prefill） | 0.98s | 7.5K token 冷启动 |
| **块屏蔽（缓存命中）** | **0.06s** | 同一序列，只算新 token |
| 文本删除 | 0.06–0.20s | 序列变了，需按新序列 prefill |

上下文越长，差距越大：1.2K 时 2.1×，2.4K 时 3.6×，3.8K 时 **8.6×**（块屏蔽的耗时基本恒定，删除随长度线性增长）。

### 3.4 位置预算（独立于屏蔽）

把证据放在开头、问题推到远处（KV 始终只有约 300 token，不占显存）：

| 位置间隙 | 命中 |
|---|---|
| 0 / 8K / 32K | 6/6 |
| **80K** | 3–4/6（格式对、值错） |
| 160K | 0/6（输出崩坏） |

注意力诊断（最后一个问题 token，全层全头平均）：

| 间隙 | 文档注意力质量 | 文档内熵 | top1 占比 |
|---|---|---|---|
| 0 | 0.169 | 0.888 | 7.7% |
| 32K | 0.112 | 0.905 | 4.1% |
| **80K** | **0.068** | 0.907 | 3.7% |
| 160K | 0.242 | 0.951 | 2.1% |

**失败是逐步的**：先丢"定位精度"（top1 减半），再丢整体（位置混叠、注意力均匀）。

**位置压缩可以恢复**：160K 间隙压到 40K 有效距离后，命中率 0/6 → 6/6；80K 间隙压到 40K，4/6 → 6/6。token 一个不动，只改位置编号。

### 3.5 案例：绝区零 2.0–3.2 版本可见性

数据：Fandom wiki（CC BY-SA），118 个 2.0+ 文档，62 道判别题，4 个知识截止版本（2.0/2.4/2.7/3.2）。

| 条件 | 闭卷 | 全塞 | 块屏蔽 | 文本删除 |
|---|---|---|---|---|
| 该答（可见） | 0/60 | 58/60 | 58/60 | 58/60 |
| 该拒答（受限） | 0/60 | **泄漏 58/60** | **0/60** | 0/60 |

闭卷 0/60 说明语料干净（模型确实不知道 2.0+ 内容）；屏蔽把越界从 58 条压到 0 条。

## 4. 工程规则

```
① 屏蔽比例：没有观察到上限（0–97% 都试过），可以按业务需要遮
② 位置预算：单个请求的总位置跨度 ≤ 32K 最稳，40K 是上限（本模型）
③ 超预算时：压缩位置轴（pos × s, s<1），不要放大、不要重排
④ 压缩必须发生在 prefill 时（K 在写缓存时就被旋转了）
⑤ 缓存复用：只要 token 序列不变，改标签不失效（16× 提速）
⑥ 拒答：靠提示词或训练，屏蔽只保证"读不到"，不保证"说不知道"
```

### 位置预算标定流程（换模型时重跑，约 1 分钟）

```
序列 = [系统提示 + 证据 ~200 token] + [问题 ~20 token]
position_ids = 证据 0..L-1，问题 L+gap..L+gap+q
gap ∈ {0, 8K, 32K, 80K, 160K}
命中率跌破 90% 的 gap 即该模型的位置预算
```

## 5. 讨论

### 5.1 为什么屏蔽不能提升质量

屏蔽去掉了竞争者，理论上能让注意力更集中。但实测"可见 vs 屏蔽"的准确率相同（22/24 = 22/24）。原因在注意力诊断里：失败不是"份额不够"，而是"文档内定位不清"（top1 仅 3.7%，熵 0.9）。把一块模糊的光斑调亮，仍然是模糊的。

### 5.2 拒答是独立的一层

屏蔽后模型不会说"我不知道"，而是编一个**不同**的答案（不构成泄漏，但不理想）。

- 块屏蔽：拒答 0–1/6
- 文本删除：拒答 5–6/6

推测原因：文本删除让上下文"看起来完整但缺内容"，模型会承认缺失；块屏蔽让上下文"看起来完整"，模型倾向于正常作答。这一层需要提示词或训练解决。

### 5.3 已缓存 KV 能否改位置（未定论）

RoPE 是旋转，理论上可用 `R(p'−p)` 直接改写缓存里 K 的位置，代价是 `O(token × head_dim)` 的逐元素乘法。局限：

- 第 0 层的 `k_raw` 与位置无关，重旋转应精确；
- 更深层的 `k_raw` 已经"看过上下文"，重旋转只改几何、不改内容，是近似。

我们的数值验证（`R(d)·K(p) == K(p+d)`）目前相对误差约 10%，未通过，推测是旋转约定或精度问题，**尚未定论**。

### 5.4 为什么是现在：三条曲线在收敛

本文的方法并不新——"只读一部分块"是稀疏注意力的老想法。真正变化的是**代价结构**：三件事同时发生了。

#### 曲线一：每 token 的缓存成本在断崖式下降

| 代际 | 每 token KV | 相对 Qwen3-1.7B | 来源 |
|---|---|---|---|
| DeepSeek-V1 | ≈ 380 KiB（按 437× 反推） | 3.4× | README 推算 |
| Qwen3-1.7B（GQA 28×8×128，bf16） | 112 KiB | 1× | 本实验 config |
| DeepSeek-V3.2（MLA 61×(512+64)） | 68.6 KiB | 0.61× | 官方 config |
| DeepSeek-V4-Flash | ≈ 3.5 KiB | 0.031× | 按 V4.1 = 1/4 推算 |
| **DeepSeek-V4.1-Flash**（FP4 + CSA2 + CED） | **890 B** | **0.0078×** | 官方模型卡 |

从 V1 到 V4.1 是 **437×**（README 原文）。这不是量变——**同样 2.9 GiB 的 KV 预算，能装的内容从几万 token 变成几百万**。

#### 曲线二：上下文窗口在变长

| 模型 | 声明窗口 |
|---|---|
| Qwen3-1.7B | 40,960 |
| DeepSeek-V3.2 | 163,840 |
| **DeepSeek-V4.1-Flash** | **1,048,576（1M）** |

窗口变长意味着"一次 prefill 覆盖全语料"从假设变成现实；但**窗口越长，一次性塞进去的竞争者也越多**，可见性管理反而更必要。

#### 曲线三：块粒度索引已经是原生设计

V4.1-Flash 的 config 里直接有：

```
candidate_block_size      = 8
index_topk                = 512
candidate_topk_blocks     = 2048
kv_source_layer_ids       = [2, 8, 14, 20]      # 跨层共享 KV
index_source_layer_ids    = [2, 8, 14, 20, ...] # 跨层共享索引
```

也就是说，**"引擎持有块表、按规则选择读哪些块"已经是新一代架构的默认形态**。我们的工作只是把这个块表**再用一层业务语义（谁能看）驱动**——从"按相关性选块"扩展到"按权限选块"。

#### 三条曲线合起来说明什么

```
缓存变便宜  →  重 prefill 的浪费占比上升（算力已经花掉，却要重算）
窗口变长    →  可见集管理从"可选"变成"必须"
块索引原生  →  控制面已经存在，只差一层业务标签
```

过去"每次重拼上下文"是合理的，因为缓存贵、窗口短、引擎没有块级控制。**现在这三个前提同时反转了**。

反过来看，这也是一个**接口设计问题**：引擎已经能按块选择，但它只接受"内容相关性"这一种信号；而多角色/多租户/多时间线场景需要的是"身份与权限"信号。本文主张把这个信号也变成引擎的一等输入。

#### 一个可检验的预测

如果上述趋势成立，那么在没有块级可见性接口的引擎上，业务方会怎么绕过？

1. 拼多份缓存 → 容量线性膨胀；
2. 或者退回提示词约束 → 可被诱导。

两者都会随窗口变长而更快失效。**这是一个可以被后续工作证伪的判断**，也是我们认为这项工作值得现在做的理由。

## 6. 局限

1. **位置预算只测了一个模型**（1.7B）。更大或长上下文训练的模型应该更大，但未测。
2. **"屏蔽提升质量"未验证**：只测过随机干扰，没测误导性干扰。
3. **真实 80K 上下文未跑**（显存不够），80K/160K 只有位置间隙模拟。
4. **数据集规模小**：62 题，且全是 infobox 事实（身高/生日），属单跳查表，不是完整 benchmark。
5. **判分为子串匹配**，未做人工复核。

## 8. 结论

上下文掩码提供了一条**不改变 token 序列**的可见性控制路径：屏蔽精确、质量无损、缓存可复用、速度为 16×。它与位置预算正交——屏蔽决定"能不能看"，位置决定"看不看得清"，后者有约 32K 的模型相关预算。

在世界观 RAG 中，这套机制让 N 个角色共享一份 prefill 缓存，只需为每个角色维护一张不长的块黑名单，从而在架构层面消除信息泄露，而不是依赖模型自觉。

更一般地说，它把**上下文管理从 agent 侧移到引擎侧**：agent 只声明"我是谁、我处在什么进度"，引擎负责"这份缓存里哪些块对它可见"。随着缓存变得更便宜（量化、offload、层级共享），这个迁移的收益会继续放大。

### 9.3 踩坑记录（这部分对复现者最有价值）

| 坑 | 现象 | 原因 | 修法 |
|---|---|---|---|
| **白名单语义** | 输出退化、答非所问 | 把模型自己生成的块也屏蔽了 | 改黑名单：只列不可见块 |
| **块区间算法** | 掩码"没生效" | 在追加段落**之后**才取起点，每段只遮最后 1 块 | 起点在追加前取，补零宽字符到 16 边界 |
| **判分过严** | 准确率虚低 | `166cm` 与 gold `166cm (5'5")` 被判错 | 前缀匹配 |
| **生成截断** | 答案被切一半 | `max_tokens=20` 太小 | 提到 32 并检查换行 |
| **非单调位置** | 输出乱码 `(((((` | 手动改 `position_ids` 破坏递增 | 位置必须单调 |
| **位置拉伸** | 16K 就崩 | `pos × 4` 改变了相邻 token 距离，分布外 | 压缩（s<1）可以，放大不行 |
| **禁用 flashinfer 采样** | 启动报 sm75 | RTX 5060 是 sm_120 | `VLLM_USE_FLASHINFER_SAMPLER=0` |
| **fp8 KV 不被支持** | 启动失败 | `FLEX_ATTENTION` 不认 `kv_cache_dtype` | 只能用 bf16 |
| **pkill 自杀** | 命令把自己杀了 | `pkill -f` 匹配到自身命令行 | 把 pkill 放进 `.sh` 文件再调用 |
