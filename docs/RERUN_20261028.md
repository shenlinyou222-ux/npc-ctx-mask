## 2. 新测：三个更硬的 TTFT 数字（此前是单点）

`scripts/_ttft_probe.py`，6.7K token / 420 块，每轮用段落轮转构造新序列保证冷启动，rep=3：

| 臂 | 含义 | TTFT（rep1/rep2） |
|---|---|---|
| `A_cold` | 全塞，首次 prefill | **1.286 s / 1.271 s** |
| `A_warm` | 全塞，重复 | 0.073 s / 0.062 s |
| `M_warm` | **同 token 序列，只换可见性（遮 17% 块）** | **0.064 s / 0.074 s** |
| `D_cold` | 删掉中段文本（序列在中途分叉） | **0.518 s / 0.515 s** |
| `D_warm` | 删文本版重复 | 0.060 s / 0.056 s |

三句话：
1. **前缀复用 = 18–20×**（1.28 s → 0.065 s）；
2. **可见性变化 = 0 惩罚**（M_warm ≈ A_warm，差 1–3 ms，在噪声内）；
3. **改文本 = 8× 代价**（D_cold 0.515 s，是热态的 8 倍）——即使只删中段 17% 的块，分叉点之后的块全部要重算。

这比原来"0.98 → 0.06"更有说服力：原来那只证明了"前缀缓存有效"（vLLM 本来就有），新数据证明的是**"换可见集不破缓存，换文本才破"**。

## 4. 三个必须修的数据问题

### 4.1 仓库里的三份结果 JSON 是"掩码没生效"时跑出来的

| 文件 | 里面对不上的地方 | 本次复跑 |
|---|---|---|
| `results/zzz_bench.json` | M 臂泄漏 **60/60**（= A 臂），但论文写 M 0/60 | M 0/60 ✅ |
| `results/baroque_v2.json` | M 臂"该拒答"泄漏 **5/5**（= A 臂） | M 0/5 ✅ |
| `results/multihop_bench_v2.json` | M 泄漏 12/17 > A 11/17 | M 4/9 vs A 5/9 |

**论文的数字是对的，但仓库里的原始数据不支撑它们。** 这三份已被 `results/*_20261028.json` 取代（旧文件保留，README 已标注 superseded）。

### 4.2 逐臂 TTFT 有顺序混淆，不能直接用

`zzz_bench` 每题固定按 A → M → D 发请求，A 永远吃冷 prefill、M/D 永远吃热缓存。
所以文件里 A 0.131 s vs M 0.049 s 的"2.7×"**不是掩码的功劳，是执行顺序的功劳**。
本轮已用独立的四点测量替代（§2）。

### 4.3 掩码配置按 mtime 重载，写入后必须等一下

`_npc_vis._load_cfg()` 用 `(path, mtime)` 做缓存键。脚本"写 JSON → 立刻发请求"时，若两次写入落在同一个 mtime 分辨率内，服务端会**静默沿用上一份位图**。
这很可能就是 4.1 那三份坏数据的根因。修法（二选一）：写入后 `sleep 0.05`（本轮探针采用），或在 JSON 里放一个自增序号并纳入缓存键。
