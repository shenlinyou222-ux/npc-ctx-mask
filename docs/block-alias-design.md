# 块表别名：让子智能体把结果写进主序列的槽位

## 问题

主智能体分叉时预留一块槽位 `[P, P+L)`，子智能体算完后要把结果写进去。试过两种做法：

| 做法 | 结果 |
|---|---|
| 给子请求加 `start_position = P` | **崩溃**（CUDA illegal memory access） |
| 全量重 prefill（文本拼回） | ✅ 可行，但与 KV 拼接行为等价（20/20 = 20/20） |

崩溃原因：vLLM 的块表按 `position // block_size` 索引。

```
换位置不改块表:  position 1000 -> block 62, 但只分配了 8 块 -> 越界
```

**位置和块表必须一起改。**

## 想要的机制：块表别名

vLLM 已经有块共享的底层设施——`block_pool` 的引用计数，前缀缓存就用它去重：

```python
# vllm/v1/core/block_pool.py
block.ref_cnt += 1     # 共享
block.ref_cnt -= 1     # 释放（归零才回收）
```

缺的只是"**按 id 指定共享**"的入口：现在共享只发生在"满块 + 内容哈希相同"的前缀缓存路径上。

## 设计

```
主请求 A：
  prompt = S + [L 个占位 token] + 问题
  -> 槽位块 b1..bk 被真实分配，A 的块表里有它们
  -> A decode 期间这些块被掩码遮住

子请求 B：
  block_table = [b1..bk]        # 别名，ref_cnt++
  start_position = P            # 与槽位位置一致
  prompt = 子智能体的任务
  -> 生成的总结 K/V 直接写进 b1..bk（零拷贝）

返回：
  A 解除对 b1..bk 的掩码 -> 下一次 decode 就能读到总结
```

## 为什么这样就对

| 顾虑 | 为什么不是问题 |
|---|---|
| K 里的旋转是写入时的位置 | 子请求的 `start_position` 就是 P，写入时位置已经对齐，**不需要重旋转** |
| A 释放会不会连累 B | `ref_cnt` 保证块在被引用时不被回收 |
| 要不要拷贝 | 不要，直接写同一块显存 |
| 块粒度 | 槽位按 16 token 对齐，正好是块大小 |

对比另外两条路：

| 方案 | 代价 |
|---|---|
| 文本重 prefill | 有效，但每次返回都要重算槽位附近所有 token |
| K/V 重旋转后注入 | 数学上精确，但我们的数值验证未通过（~10% 误差），且深层只是近似 |
| **块表别名** | **零拷贝、零重算、位置天然正确** |

## 改动范围（估计）

| 位置 | 改动 |
|---|---|
| `kv_cache_manager.py` | 新增 `alias_blocks(req_id, block_ids)`：拿块、`ref_cnt++`、写进 `block_table` |
| `scheduler.py` | 请求可携带预分配的块 id；跳过常规分配 |
| `model_runner.py` | `positions` 从 `start_position` 起（**必须与块表同时生效**，否则就是本文开头那个崩溃） |
| API | 请求体新增 `kv_alias: {blocks: [...], start_position: int}` |

## 与掩码的关系

两者独立、可组合：

- **掩码**决定"谁现在能读这块"；
- **块表别名**决定"这块里装的是谁的 K/V"。

合起来才是完整的"分叉-并行-汇总"：

```
掩码（写之前：挡住旧的）
  -> 别名写入（子智能体写进槽位）
    -> 解掩（写之后：放开新的）
```
