# 多智能体协议（实测版）

模型：Qwen3-4B-AWQ，vLLM + FLEX_ATTENTION 掩码。

## 协议

```
① 主智能体一次接收全部问题，并预留 N 段空位
② 子智能体 k 在 [P_k, P_k+L) 上产出结论（锚定该位置生成）
③ 谁返回，就为谁做一次 prefill：
      「The sub-agent for Qk has returned.
        Answer Qk only.
        Then reply exactly "I don't know" for the others.」
④ 解除第 k 段掩码
⑤ 主智能体只回答 Qk
```

## 三个关键要素，每个都有对照

### 1. 必须说 **only**，不能说 first

| 通知 | 全可见时答对 |
|---|---|
| "Answer Q2 **first**" | **2/6** |
| "Answer Q2 **only**" | **18/18** |

"first" 挡不住它按问题列表顺序作答；"only" 才有效。

### 2. 必须显式禁止填其他空

只留段 2、只问 Q2：

| 通知 | Q2 答对 | 其他题被填上段 2 的码 |
|---|---|---|
| 无协议句 | 6/6 | **10 次** |
| 加「其余答 I don't know」 | **6/6** | **0 次** |

模型有"不留白"倾向：只要能看到一点内容，就把所有问题都填上。加一句禁止即可归零，且不损失命中率。

### 3. 通知必须在**返回时**prefill，不能改前面的上下文

否则前缀缓存失效，16× 的提速就没了。实测这条 prefill 只影响之后的 token，前面已生成的 KV 不变。

## 已排除的伪问题

| 现象 | 实际原因 |
|---|---|
| 4B "多实体对不上"（all 2/6） | 是 "first" 措辞导致按列表顺序答，**不是**模型缺陷。改成 only 后 18/18 |
| 1.7B 在同样协议下 0/4 ↔ 3/4 抖动 | 1.7B 确实扛不住多步协议；4B 稳定 |

## 多实体能力基线（全可见，4B）

```
one_q    18/18   每次只放一个问题
three_q  18/18   三题一起摆，要求三行作答
seq_q    18/18   三题一起摆，只回答点名那一题
```

**多实体本身不构成瓶颈。**

## 未验证

- 同一请求内连续多次解除掩码（需引擎支持中途改掩码）；
- N > 3 的槽位；
- 7B / 更大模型上的同一协议。
